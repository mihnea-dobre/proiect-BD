# 17. a. Realizarea normalizării BCNF, FN4, FN5.

## BCNF (Forma Normala Boyce-Codd)

**Definitie**: O relatie este in BCNF daca pentru orice dependenta functionala netriviala X->Y, X
este super cheie.

*Exemplu de incalcare*:
Sa presupunem ca in tabelul `MASINA` am fi avut o proprietate `nume_user` si `nr_matricol` ar fi fost cheie candidat.

**MASINA**(#id_masina, nr_matricol, este_elec, id_user, nume_user)

Am fi avut dependentele:
- `id_masina -> nr_matricol, este_elec, id_user, nume_user`
- `nr_matricol -> id_masina, este_elec, id_user, nume_user`
- `id_user -> nume_user`   

Aici, ultima dependenta `id_user -> nume_user` incalca BCNF deoarece id_user nu este super cheie (acestea fiind `id_masina` si `nr_matricol`). `nume_user` depinde de un atribut non-cheie.

__**Normalizare**__

Separam in doua tabele.

**MASINA**(#id_masina, nr_matricol, este_elec, *id_user*)
**USERS**(#id_user, nume_user, .....)

Este aproape exact relatie care exista in proiectul actual.

## FN4

**Definitie**: O relatie este in FN4 daca pentru orice dependenta multivalorica netriviala X->->Y, X este super cheie.

*Exemplu de incalcare:*

Sa presupunem ca am fi avut un tabel LOC_ZONA care ar fi stocat informatii despre locuri si tipuri de zone.

**LOC_ZONA**(#id_loc, id_zona, tip_zona)

Un loc (`id_loc`) poate fi asociat cu mai multe zone (`id_zona`), independent de `tip_zona`.
Un loc (`id_loc`) poate avea mai multe `tip_zona`, independent de `id_zona`.

Asta creeaza dependente multivalorice:
id_loc ->-> id_zona
id_loc ->-> tip_zona

Ambele incalca FN4 deoarece id_loc nu este super-cheie, ci cheie compusa.

__**Normalizare**__

Spargem in doua tabele:

**LOC_ZONA_1**(#id_loc, id_zona)  (in proiect este defapt relatia `SPATIU_PARCARE`)
**LOC_ZONA_2**(#id_loc, tip_zona)

In proiect, se rezolva cu specializarea zonelor: `ZONA_ALBASTRA`, `ZONA_VERDE`, `ZONA_REZIDENTIALA`.

## FN5

**Definitie**: O relatie este in FN5 daca orice dependenta de join este implicata de cheile candidate.

*Exemplu de incalcare:*

Daca am fi avut un tabel `REZERVARE_DETALII` care combina informatii din trei tabele separate:

**REZERVARE_DETALII**(#id_rezervare, id_masina, id_loc, id_user)

cu dependenta de join:
- (id_masina, id_loc) ⋈ (id_masina, id_user) ⋈ (id_loc, id_user)

Este o dependenta join netriviala care nu este implicata de chei candidate (in acest caz `id_rezervare`).

__**Normalizare**__

Descompunem in trei tabele.

**REZERVARE**(#id_rezervare, id_masina, id_loc)
**MASINA**(#id_masina, id_user)
**LOC_PARCARE**(#id_loc, ...)

Asta corespunde aproape exact cu ce este deja in proiect.

# b. Aplicarea denormalizării, justificând necesitatea acesteia.

**Justificare**: Modelul normalizat este corect teoretic, dar cateodata avem interogari frecvente care pot necesita
join-uri costisitoare. Pentru a imbunatati performanta, putem introduce date redundante care adauga lucru suplimentar in moment
dar reduce costul interogarilor pe termen lung.

*Exemplu de denormalizare:*
Daca avem o interogare "afiseaza pentru fiecare utilizator ultima rezervare facuta si numarul total de rezervari", asta necesita un left join intre `USERS`, `MASINA` si `REZERVARE`, plus o grupare si functie de agregare.

*SQL normalizat:*
```sql
SELECT u.id_user, u.nume,
       MAX(r.data_inceput) AS ultima_rezervare,
       COUNT(r.id_rezervare) AS numar_rezervari
FROM USERS u
LEFT JOIN MASINA m ON u.id_user = m.id_user
LEFT JOIN REZERVARE r ON m.id_masina = r.id_masina
GROUP BY u.id_user, u.nume;
```

Pentru a optimiza aceasta interogare putem adauga doua coloane redundante in tabelul USERS:
`ultima_rezervare` (TIMESTAMP) - data celei mai recente rezervari
`numar_rezervari` (INT) - numarul total de rezervari

Aceste coloane vor fi actualizate automat printr-un TRIGGER. Va fi muncitoresc sa implementam, dar va avea un efect masiv.

Pasi:
- 1. Adaugam coloanele.
- 2. Initializam datele existente.
- 3. Cream trigger-ul.
- 4. Facem inca o data interogarea.

```sql
--Adaugam coloanele.
ALTER TABLE USERS ADD (ultima_rezervare TIMESTAMP);
ALTER TABLE USERS ADD (numar_rezervari INT DEFAULT 0);

--Initializam datele existente.
UPDATE USERS u
SET (ultima_rezervare, numar_rezervari) = (
    SELECT MAX(r.data_inceput), COUNT(r.id_rezervare)
    FROM MASINA m
    LEFT JOIN REZERVARE r ON m.id_masina = r.id_masina
    WHERE m.id_user = u.id_user
);

--Trigger
CREATE OR REPLACE TRIGGER trg_rezervare_denormalizare
AFTER INSERT OR DELETE ON REZERVARE
FOR EACH ROW
BEGIN
    IF INSERTING THEN
        UPDATE USERS
        SET numar_rezervari = NVL(numar_rezervari, 0) + 1,
            ultima_rezervare = :NEW.data_inceput
        WHERE id_user IN (
            SELECT m.id_user
            FROM MASINA m
            WHERE m.id_masina = :NEW.id_masina
        );
    ELSIF DELETING THEN
        UPDATE USERS
        SET numar_rezervari = NVL(numar_rezervari, 0) - 1,
            ultima_rezervare = (
                SELECT MAX(r.data_inceput)
                FROM MASINA m2
                JOIN REZERVARE r ON m2.id_masina = r.id_masina
                WHERE m2.id_user = (
                    SELECT m.id_user FROM MASINA m WHERE m.id_masina = :OLD.id_masina
                )
            )
        WHERE id_user IN (
            SELECT m.id_user
            FROM MASINA m
            WHERE m.id_masina = :OLD.id_masina
        );
    END IF;
END;
/

--Interogarea echivalenta, dupa denormalizare
SELECT nume, ultima_rezervare, numar_rezervari
FROM USERS;
```
